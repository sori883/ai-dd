# ADRへの名称統一とUnit実行stateの具体案

状態: ADRへの名称統一はユーザー指定で確定。以下のstate項目と動作は検討案で、実装未承認。

## 名称と記録の責任

ユーザーの「KDRの文章をADRに統一して」により、今後の説明・現行設計では記録文書をADRと呼ぶ。
1 Intentにつき1 ADRとし、目的・各工程の判断・結果・検証・残件を同じOKF Markdownへ記録する。
目的決め、未確定事項の深掘り、Unit分割、実装、検証、統合、再開の各場面で、必要に応じてOKFを参照する。
参照した知識と判断への影響もADRへ記録する。

名称について[直前の案](2026-09-08-kdr-unit-state-sensor-proposal.md)と以前の記録を置換する。
過去の判断・実装証拠は当時の名称のまま保持する。既存CLIの `kdr`、型名、ファイル名、Concept IDは
現在の実装を正確に表す識別子であり、この文書編集で変更済みとは扱わない。
製品の表示・テンプレート・CLI・保存形式への改名反映は、対象と影響を示す実装計画にまとめる。

## 管理するstateの案

実行stateはUnit単位の現在の割当をローカルファイルに保存する。メモリ内だけには置かない。
この案の「一時」とは、再開に使うが成果の正本にはせず、Git共有の判断記録とは分けるという意味である。
具体的なファイル形式・パスは未確定。既存の `aidlc/.runtime/` を候補とする。

| 項目 | 例 | 必要な理由 |
| --- | --- | --- |
| Space・Intent ID・Unit ID | shop / 固定Intent ID / api | 別の目的やUnitの実行と混同しない |
| 実行ID | run-03 | 同じUnitの再試行と古い担当からの遅れた結果を区別する |
| 調整役・担当session | coordinator-1 / worker-2 | 誰が割当と結果回収を担当するか分かる |
| 作業場所と開始版 | worktreeの場所・開始commit | どのコードを変更中か再開時に確認する |
| 割当時のADR計画版 | ADRの内容hash | 実行中の計画変更を検出し、現在の計画と照合する |
| 実行状況 | 起動待ち / 実行中 / 結果確認待ち / 再開確認待ち | 二重起動と未回収結果の見落としを防ぐ |
| 待機理由・引渡し先 | 質問待ち、停止、結果の参照先 | 待っている理由と回収すべき結果を特定する |

実行IDや計画版は全操作auditや成果物snapshotではなく、現在の割当を取り違えないための値である。
最終確認時刻を補助表示に使うとしても、時刻だけで担当の停止を認定しない。

## 開始・終了・中断の扱い

1. ADRのUnit計画と依存先の統合結果をSensorで確認する。現在の割当がなければ、競合しない形で
   起動待ちの割当を保存してから担当を起動し、起動が確認できたら実行中にする。
2. 担当が結果を返したら結果確認待ちにする。担当終了だけではUnit完了にしない。
3. 調整役が成果物と検証を確認し、必要なレビュー・統合を行い、結果をADRへ保存する。
   保存済みの結果と実行IDを照合してから割当を解放する。ADR保存失敗時は結果確認待ちを残す。
4. 編集失敗ではUnitは実行中のまま、担当が再思考・修正を続ける。質問待ちも理由を付けて割当を保持する。
5. 担当や調整役の停止・連絡断で実状が不明なら再開確認待ちにする。再開時にはADR・worktree・
   実際の担当を照合する。保存されたstateが実行中でも、その値だけで稼働中とは判断しない。
   状態ファイルの消失も未着手とは扱わず、再割当前に既存作業を確認する。

起動前後やADR保存後に停止する場合もあるため、上記は一つのtransactionとはみなさない。
再開時に境界の途中を検出・照合できることを受入条件にする。失効時間だけで重複担当を起動しない。

## ADRから読み取る情報とSensor

Unitの目的、Boltへの所属、依存関係、変更範囲、必要成果物、受入条件、確定結果はADRを正本にする。
「未着手」「依存待ち」「統合済み」などの一覧表示はADR・現在の割当・Sensorから導く。
Boltの完了も所属Unitの統合結果から判定し、独立した完了台帳を増やさない。
既存sessionのIntent対応・未記録・実行中tool・Rule読込確認は、Unit割当とは役割が異なるため維持する。

Sensorは読取り専用で、ADRの対象ID・必要記録、計画で宣言した成果物、依存先の統合、
テスト・レビューとコード対象版の一致を検査する。「成立」「不足」「確認不能」を返し、
stateの値やファイルの存在だけで品質・承認・完了を認定しない。操作の許可はCLI/hook側で決める。
各Sensorの拒否条件と、本家AI-DLCの助言Sensorからの意図的差分は実装前の計画で提示・確認する。

例: apiとuiは独立したUnitとして並列実行できる。apiの担当が終了しても結果確認待ちであれば、
その成果を必要とする結合検証Unitは開始しない。apiとuiが統合され、ADRに検証対象版と結果が記録されてから始める。

Go単一バイナリ、SpaceのknowledgeへのOKF集約、外部Go module追加なしを維持する。
この記録はstate契約の説明案であり、コード・設定・Issue・PRを変更する実装許可ではない。
