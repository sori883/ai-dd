# Git不要化では旧記録の後方互換と移行を要求しない

日付: 2026-09-11。状態: 後方互換不要のユーザー指定。具体計画の説明を継続中で、実装は未着手。

ユーザーは集合SHA方式の具体計画に対して、次を指定した。

> 旧記録などの後方互換は無視して良いです。

この回答は、今回のGit不要化で変更するstate、Unit、テスト結果、担当管理の旧記録にも適用する。[集合SHA方式の記録](2026-09-11-git-independent-content-sha-approved.md)と[実装計画](../../design/git-independent-workflow-plan.md)のうち、旧配置の切替・復元・旧記録対応を今回の実装範囲に含める部分を置き換える。

- 新しい保存形式を直接設計し、旧記録を読めるようにする機能、変換処理、新旧の二重運用、旧版との互換テストは作らない。
- 旧記録を新しいSHA形式へ自動変換したり、古いテスト・レビュー・承認を新方式へ流用したりしない。
- 既存ファイルの実際の削除や、利用者の環境・設定の一括初期化を指示されたとは解釈しない。今回の開発は新規の検証用配置と新形式を対象に進める。
- 新形式自体の入力検証、保存競合・保存失敗からの復旧、同じ要求の再試行は必要であり、後方互換とは区別する。

ユーザーは同時に「Git履歴に代わるUnit成果の内容照合」「同じフォルダでの順次作業」「新しい保存形式」の説明を求めた。この発言を、それらの具体契約や計画全体の実装承認とは扱わない。Git不要化と適切な範囲のSHA方式は既に指定済みで、再確認しない。

説明は、Unitを分けた作業の一単位として定義し、次の意味を明確にする。

1. 内容照合は、担当が提出した検証範囲のSHAと、調整AIが現在の成果から再計算したSHAが一致することをCLIで確認すること。同じフォルダなら、ファイルのコピーやGit mergeを行う必要はない。内容が正しく動くかはテストと独立レビューで確認する。
2. 順次作業は、同じ作業場所の実装担当を一人ずつにし、前の担当の処理停止・成果回収を確認してから次の担当を割り当てること。各Unitの実装を終えたら最新全体で検証し、別エージェントがレビューする。担当を分けるためにcloneを増やさない。
3. 新しい保存形式は、既存のJSONによるstate・結果・担当管理を使いながら、Gitコミットを前提とする項目を、検証パス集合・集合SHA・Unit/runの対応へ変更すること。文書を新しい独自台帳へ移したり、利用者がファイルごとのSHAを登録したりすることではない。

RAMと計画の文書だけを更新する。製品コード・設定・Issue・PR、利用環境、旧記録は変更せず、実装テストも実行しない。
