# 共通project配下に複数アプリを置き、ブランチを順次処理する

日付: 2026-09-11。状態: ユーザー指定の構成と方向性。Gitの管理単位は確認が必要。

ユーザーは、管理用・実装用・レビュー用のcloneを隣に並べる説明について「イメージと違いました」と訂正し、次の配置を示した。

```text
project/
├── .codex/
├── aidlc/
├── アプリケーション1/
└── アプリケーション2/
```

さらに「worktreeは必須ではなく１ブランチずつ処理出来ればいい」と指定した。ユーザーが求めるのは、共通のprojectの下にAI-DLCの管理領域とアプリケーションを置く構成であり、管理用・worker用・reviewer用の別cloneを必須にする提案ではない。

この指定を今後の設計の基準とする。[通常cloneを担当別に分ける案](2026-09-11-worktree-deferral-layout-options.md)は未採用の検討履歴として保持する。[worktree共有hook計画](../../design/shared-worktree-hooks-plan.md)をこの回答で承認済みとはせず、その計画による実装へは進まない。既存worktree機能や利用ファイルの削除、ブランチ切替や未コミット変更の破棄を依頼されたものとは解釈しない。

## 指定構成に合わせる方向

- メインAIは共通の `project/` を開く。Codexのagent・hookは `project/.codex/`、既存のCLI操作Skillは `project/.agents/skills/` に置く。
- workflow、Space、Intent、Knowledge、ADR、Rule、ローカルの会話・担当管理は `project/aidlc/` 配下に置く。アプリごとに独立したAI-DLC管理領域を自動作成しない。Spaceの分け方は今回新しく指定されていない。
- 各アプリのソースコードは `project/アプリケーション1/`、`project/アプリケーション2/` 配下に置く。実装計画で対象パスを示す。
- 一つの作業フォルダでブランチを順に扱う運用を基本案にする。同じコードを変更する実装担当は一人ずつにし、複数worktreeによる同時実装を必須にしない。Unitによる作業分割と、実際の並列実行は区別する。
- 独立レビューは別の担当・会話で行う原則を保つ。同じフォルダを使う場合の対象版の固定と、レビュー中のコード変更をどう防ぐかを具体計画へ含める。

現在は `src/internal/assignment/reservation.go` の `workerRoot`、`src/internal/flow/unit.go` のclaim、`src/internal/flow/review.go` のReviewが、worker/reviewerに管理元とは別のrootを要求する。このため、提示された方向は既存設定を変えるだけで完全に利用できる状態ではない。別root必須条件、順次割当、コード版の保持、ブランチ切替時の既知処理・未保存成果の扱いを見直す必要がある。OS上の全process監視や、終了不明の予約の自動解放は追加しない。

## まだ決まっていないこと

提示されたディレクトリ図にはGitの管理単位が含まれていない。`project/.git/` 一つで全アプリを管理する場合は、ブランチ切替が全アプリに共通で効く。各アプリがそれぞれ `.git/` を持つ場合は、アプリ別のrepository・branch・commitをAI-DLC側で扱う契約が必要になる。両者を同じ設計と見なさず、ユーザーへ一問で確認する。

現時点では会話の訂正と実装上の影響を記録しただけで、コード・設定・Issue・PRの変更、ブランチ切替、テスト実行はしていない。Gitの管理単位が決まった後、指定構成に沿った自己完結した修正計画へまとめる。
