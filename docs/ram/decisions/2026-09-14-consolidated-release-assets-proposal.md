# 実行ファイルを分けたままRelease添付をまとめる案

2026-09-14。ユーザーはコマンドによる自動導入の案を聞いた後も、
「43個はどうしても減らせないのかな？」と確認した。
手動選択をなくすだけでなく、添付ファイルそのものの削減を検討する。

## 確認できた現在の構成

現行の43件は、5CLIそれぞれについて6つのOS・CPU向けarchiveと
manifest・checksumの2件を作る40件に、共通資材の3件を加えた数である。
これは現在の梱包方式であり、5つの独立した実行ファイルを維持するための必須数ではない。
`src/cmd/aidlc-dist/release.go`がこの梱包を生成し、
`src/internal/install/release.go`が製品別のmanifest・checksum・archiveを取得する。

## 新しい提案

次版では、OS・CPUごとに5つの独立CLI、共通/Codex資材、内容一覧、ライセンスを
一つのarchiveへまとめる。macOS・Linux・Windowsのamd64・arm64で6件、
全archiveを照合する共通`SHA256SUMS`を1件として、製品が添付する配布物を7件にする。
これは使いやすさと対象環境ごとの取得を両立する推奨案で、理論上の最小数という主張ではない。

各archiveの中でも`aidlc-install`、`aidlc`、`okf`、`natural-japanese-go`、`aidlc-dist`は
別の実行ファイルである。インストーラーへ本体を統合しない。
共通資材は配布時のコピーであり、ソースの共通手順を複数箇所で管理しない。
利用先に置く日常用CLIは従来の3つとし、installerとdistを日常利用に必須にしない。
一式で取得するため、開発者用`aidlc-dist`もダウンロードされるという容量上の影響はある。

コマンド導入の入口はOS・CPUを判定し、対象archiveとchecksumだけを取得・照合し、
archive内のGo製インストーラーへ渡す。インストーラーは同じarchive内のruntimeと資材を
検査して配置できるようにする。必要なライセンスや内容検査を省略して数を減らす案ではない。
取得スクリプトはリポジトリから配布する前案を引き継ぎ、Releaseの添付数に加えない。

添付だけを削除しても現行インストーラーは新構成を読めないため、
`aidlc-install`、`aidlc-dist`、共有する配布形式・検査、CI、導入文書を一緒に変更する必要がある。
公開済みv0.1.1のファイルは変更せず、新しい版の形式として提案する。
新版の番号、詳細な梱包契約、実装計画、実装・公開の許可はまだ確定していない。

## 前案との関係

[43件を維持する初回取得の案](../../design/command-line-install-entry-plan.md)は
未承認の検討履歴として保持する。本記録は、その案の「添付数の削減を含めない」範囲を
見直す追加提案であり、ユーザーが7件への変更を承認済みという意味ではない。
製品コード・設定・Issue・PR・Releaseは変更していない。
