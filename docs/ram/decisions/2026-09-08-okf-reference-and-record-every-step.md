# 作業全体でOKFを参照し、各段階の判断と結果を記録する

状態: ユーザー指定の要件。具体的な実装計画は未承認。ADRという呼称と既存KDRの関係は確認対象。

## 指示と既存方針との関係

ユーザーは[目的決定→未確定事項の深掘り→分割→実装→統合の流れ](2026-09-08-discovery-before-parallel-implementation.md)
を了承したうえで、深掘りにはOKF検索を使い、どの工程でも必要に応じてOKFを参照することを追加指定した。
また「ADR」「何をやったか」を挙げ、各工程で記録を確実に残すことを要求した。
終了時だけにまとめるのではなく、目的決定・調査・作業分割・実装・統合それぞれの記録を要件とする。

既存の合意は1 Intentにつき1 KDRである。今回の「ADR」を、別の記録形式やファイルを新設する承認と
自動的に解釈しない。まずKDRに各段階の行動・判断・結果を記す案を示し、別ADRが必要という意図か確認する。

## 計画へ反映する具体案

| 段階 | OKFで参照する内容の例 | 記録する内容の例 |
| --- | --- | --- |
| やることを決める | 既存の目的・設計・関連KDR・制約 | 目的、範囲、完成条件、その理由 |
| 未確定事項を深掘りする | 関連知識・過去の判断・設計 | 調べた問い、参照と発見、候補、採用/不採用の理由、残る質問 |
| 作業を分ける | 構成・API契約・共有設計 | Unitの境界、依存関係、並列可否の理由、担当と検証方法 |
| 実装・修正する | 必須Rule・設計・実装上の知識 | 変更、試作、失敗と修正、テスト結果、設計からの差異 |
| 統合・レビューする | 各Unitの結果・参照設計 | 統合対象、検証/レビューの対象版と結果、残件、再開点 |

OKF検索結果の要約だけを根拠にせず、判断に使う文書の本文を読み、Concept IDと参照箇所を記録する。
参照内容が変更され得る場合の版の識別方法は次期計画で具体化する。
検索で答えが見つからなければ未解決として扱い、必要な質問・追加調査へ進む。
必須Ruleの読込みは既存の必須条件を維持する。一般知識の検索は必要に応じて行い、無意味な全件再読込を要求しない。

各段階で判断・結果がまとまったとき、担当への引渡し、質問待ち・中断・終了の前に、
その時点までの結果を同じIntentの記録へ反映する。どの検索コマンドを何回実行したかを
すべて記録する全操作auditではなく、第三者が判断理由と続きの作業を理解できる記録を残す。
途中で設計や目的を見直したら、それも記録し、古い結論を現在の合意として扱わない。

並列担当の結果を調整役が正本KDRへ集約する案について、引渡し前の記録方法、未収集結果の扱い、
hookによる記録漏れの検査方法は次期の自己完結した計画に含める。新しい工程stateや全操作auditを
記録漏れ対策として再導入しない。外部moduleや旧データ移行の境界も維持する。
