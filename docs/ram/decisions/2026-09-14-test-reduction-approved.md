# テスト削減を区切って実施し、IssueとPRでマージする

2026年9月14日。ユーザーは監査結果の説明を受け、できるだけテストを削除したいと希望した。
重複・旧経路・テスト専用の補助処理、検査表と資材検査の集約、不要なGit・ビルド等の準備、
CIの重複を整理する提案に対し、「それらを削除」「区切って対応」「Issue作ってmrでマージ」
と直接依頼した。GitHubではMRに相当するPull Requestを使う。

## 実装許可

[監査](../../test-suite-reduction-audit.md)と、その監査に基づく削減案を包含する直接承認として扱う。
各区切りの具体計画とIssueを作り、単独writerによる変更、独立レビュー、read-onlyの最終検証、
現headのGitHub checks成功を確認してから、mainへPRを順次マージする。
同じ許可範囲について区切りごとの再承認は求めない。

対象はAI-DD自身のテスト・テスト専用helper/fixture、呼ばれなくなった旧内部処理、重複するCI実行。
基準の製品仕様はPR #203マージ後のmain
`adc4682ca265c9bda4434a94d9d99cff1f4b9394`である。
本家AI-DLCの新仕様を導入する作業ではなく、固定済みの製品挙動を保った検証構成の整理である。

## 保持する境界

- 保存競合、途中保存、同要求の再試行、復旧後の実file保全。
- ユーザーの承認、同じrootの二重担当拒否、親子・Intent・Unit・runの識別。
- 集合SHAが実際の対象内容を表すこと、古い結果や対象外の結果を採用しないこと。
- OKF検索とmetadata、自然日本語の独自判定、実CLIへの引数と結果の受け渡し。
- 配布の必要資材・role/権限・license・sourceの正本照合、OS固有の導入と実行。
- Git演習を外す場合でも、runtime非共有と管理された予約のないrunの拒否。

同じ保証を繰り返すテストは最も直接的な箇所へ集約する。
単純削除で独自の不具合を見逃す候補は、保証を移してから削るか、維持コストと実害を記録して残す。
残す件数やcoverage率の数値は目標にしない。新規の大量snapshotや自前汎用検証frameworkは追加しない。

公開API・保存形式・製品の承認や権限・既存配布契約は変更しない。外部Go module/toolは追加しない。
CIの合否を迂回せず、重複jobを消す際も6targetのbuild、必要なGo版の確認、race、
3OSの実配布とbootstrap検査の実行責任を明確にする。repository保護設定の変更は含まない。
Releaseの公開・tag作成はこの依頼の対象ではない。

## 運用上の判断

作業場所は `/Users/const/sori883/ai-dd-release` とし、元の `/Users/const/sori883/ai-dd` の
未commit変更には触れない。監査doc3件は前回作業の成果として最初のPRへ含める。
区切りはdocsの計画で管理し、各区切りにIssueとPRを作る。GitHub milestoneの作成は行わない。

テスト削除・既存の正しい挙動への検査集約は、残す検査の `ALREADY_GREEN` を確認して進める。
失敗を人工的に作るための製品変更や、テスト件数を埋めるためだけの追加を行わない。
製品の観測可能な不具合修正が必要になった場合は、削減に紛れ込ませず対象と回帰検査を別に判断する。

`golang-refactoring` skillの一般的な「削除ごと・マージごとの再承認」「中間集約branch」より、
今回の直接承認とリポジトリの単独writer・独立review・final・自律merge規則を優先する。
各PRを単独で正しい状態にしてmainへ取り込み、次の区切りへ進む。
