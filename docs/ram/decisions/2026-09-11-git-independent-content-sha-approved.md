# Gitに依存せず、検証対象のまとまりからSHA-256を算出する

日付: 2026-09-11。状態: Git依存撤去と集合SHA方式へのユーザー指定を記録。製品コードへの反映は未実施。

## ユーザーの指定

ユーザーは、現行SensorがGitのコミットや履歴を参照する説明に対して、次を指定した。

> git依存なしに倒したい。
> 結構gitに依存してそうだけど。

Gitなしでコード変更の自動検知を残すかを確認したところ、次の回答があった。

> ファイルからshaを算出する方法でも良いよ。

続いて、管理する単位について次の指定があった。

> ファイル個別だと大変かもだし、適切な範囲でshaを発行してね

Gitを使わず、検証する対象ファイルのまとまりからSHA-256を算出する方式を採用する。SHA-256は、ファイルの内容が同じかを比較するための値であり、Gitのコミット番号や変更履歴ではない。ファイル単位のSHAを利用者やAIが手動で登録・管理する方式にはしない。コード変更の確認をAIレビューだけに任せる案は採用しない。

## 配置とGitの関係

[共通projectとGit管理単位の整理](2026-09-11-flexible-project-git-layouts.md)のうち、「複数GitのコミットをAI-DLCが管理する」修正方向を、この記録で置き換える。配置の指定は維持する。

- `project/.codex/` にagent・hook、`project/.agents/skills/` にSkill、`project/aidlc/` に共通の管理情報を置く。
- ソースコードは `project/src/` に直接置いても、複数のアプリフォルダへ分けてもよい。
- 利用プロジェクトに `.git` がない場合も、AI-DLC自身の処理はGit実行ファイルを要求しない。
- 利用者がGitで全体や各アプリを管理することは任意。Gitを禁止したり、既存の `.git` を削除したりする指定ではない。
- worktreeを必須にせず、同じ作業場所の実装担当は一人ずつにする。独立レビューは別のエージェント・会話で行い、別cloneを必須にしない。
- 本リポジトリを開発するためのGitHub Issue・PR・CIや、配布物のビルド元情報は、利用プロジェクトでGitを必須にする依存とは区別する。

## SHAを管理する単位

基本は、Intentで検証するコード・設定・テスト・必要な共通部品を一つの範囲として、その全体に一つのSHA-256を持たせる。アプリ単体ならそのアプリと必要な共通部品、複数アプリをまたぐ変更なら関係するアプリをまとめる。単に変更担当のファイルだけを対象にすると依存する設定や共通部品の変更を見落とすため、担当範囲と検証範囲は区別する。

Unitは作業を分割する単位である。Unit単位の独立検証や別の作業場所からの成果照合が必要な場合にだけ、その検証範囲にも集合SHAを持たせる。Unitがあるという理由だけで、全ファイルのSHA管理や別の保存台帳を増やさない。

AIが対象パスと除外範囲を計画へ記載し、CLIがファイルを自動列挙する。内容だけでなく相対パスも算出対象に含め、ファイルの追加・削除・名前変更も検知する。更新日時だけで同一性を決めず、対象範囲の定義自体の変更でも古い検証結果を再利用しない。

依存物の展開先、ビルド出力、キャッシュ等の扱いを具体計画で定める。全ディレクトリを無条件に読み取る方式や、`.gitignore` の解釈を新しく実装してGit依存を別の形で再現する方式を前提にしない。成果物の文書outputsへソースコード一覧を追加せず、集合SHAと検証範囲は検証用の設定・結果として扱う。

## 実装計画で具体化する境界

- 集合SHAをテスト結果・レビュー・成果承認へ結び付け、コードが変わったら古い合格を使えないようにする。結果ファイル自身を同じコードSHAに含め、保存するたびに値が変わる循環は作らない。
- Unitの成果提出時・共通フォルダへの反映時の内容照合と、ステージ終了時の最新コード全体の検証を区別する。集合SHAはGitの履歴包含の証明にはならない。
- Git差分で実装している担当外ファイルの変更検査は、集合SHAだけでは同じ検査にならない。元の要求に含まれない網羅的な編集制限や、新しいsnapshot台帳で補わず、割当とレビューの責任を計画へ明記する。
- 通常ディレクトリの同一実体・親子関係と、同じ作業場所の二重割当を検査する。停止不明の予約を時間や結果提出だけで解放しない。
- 現行flow schema 5・assignment schema 1の記録を新しい条件で黙って有効化しない。保存形式・既存配置の扱いと復旧手順を計画に示す。
- `.git` もGit実行ファイルもない利用環境でのCLI検証と、固定Codexでの通常hook・信頼確認の実機検証を分ける。Codex側の条件をAI-DLCだけで変更できたことにしない。

この記録はユーザー指定と調査結果の保存である。SHA方式そのものの再確認は不要。コード・設定・Issue・PR・利用環境の変更やテストは行っていない。新CLI・保存形式・Unit確認方法・旧配置の切替条件を含む具体計画は、明示承認後に実装する。

[具体計画](../../design/git-independent-workflow-plan.md)に、対象パス集合とSHAの算出規則、読み取りCLI、テスト・Unit・承認の対応、旧記録の保全、新規配置、TDDと固定Codex実機gateを整理した。固定Codexの非Git project探索と通常trustはsourceを確認したが、実機のhook発火は未実測である。

独立した読み取り専用の計画確認を行い、Unit範囲のIntent全体への包含、任意深さの `.git` 除外、過去のUnit証拠と現在の合格条件の区別、targeted検証コマンド、具体計画の承認境界を補正した。これは計画の確認であり、実装後のコードレビューやテスト実行の証拠ではない。
