# 知識供給の容量・日本語・開発OSと配布OSの検証方針

- 日付: 2026-09-04
- 状態: Accepted（ユーザーが容量の機械的処理、日本語利用、開発用testと配布物の対応OSの区別を明示）
- 関連: [知識一覧の実装計画](2026-09-04-knowledge-roster-plan.md)、
  [手順不備と回復方針](2026-09-04-knowledge-roster-tdd-recovery.md)

## 背景

AIに渡す資料の一覧を作る処理の独立reviewで、Minimalの対象範囲、警告の順序、
Windows上の開発用test、容量や実fileの追加検証が指摘された。
ユーザーは、容量に独自の工夫を加える必要はなく期待どおりの動作を確認すること、
日本語で利用できること、開発環境はMacであり配布物がWindows・Mac・Linuxで動けばよいことを明示した。

## 決定

### 容量は既存ルールに従って機械的に扱う

容量上限ちょうど、わずかな超過も、承認済みの規則をそのまま適用する。
知識一覧は8,192 bytes以下の先頭部分を採用し、最初の超過以降を省略する。
警告一覧は6,144 bytes以内で省略件数の要約を確保する。短い項目の詰め直し、本文の要約、
言語ごとの特別な容量緩和などの新しい工夫は追加しない。

境界のtestは、この機械的な規則が期待どおり適用されるかを確認するために残す。
既に正しく動く条件はtestの追加だけでよく、修正のために修正を加えない。
今回の要望は既存の容量上限・選択順を変更する承認ではない。

### 日本語で利用できることを確認する

英語だけでなく、日本語の本文・file名を扱えることを検証する。
文字数とUTF-8 bytesの違いを含め、既存の容量計算法で期待どおり扱う。
既に正しい処理へ新しい日本語専用処理を加える必要はない。
原稿の一括翻訳や、原文保持・OKF非変換方針の変更は、この発言からは推測しない。

### 開発用testのOSと配布物の対応OSを分ける

開発用testはMac/Linux向けのfixtureを許容し、Windowsで全unit testを実行できるように
揃えることを、今回の採用必須条件としない。
手順不備と回復方針にある「正常系fixtureをnative絶対pathへ変更する必要がある」という
Windows上のunit test可搬性に関する必須判断は、このユーザー決定で置換する。
過去のreviewが旧条件のもとで指摘した履歴は保持する。

配布物がWindows・Mac・Linuxで動くという製品の対応範囲は縮めない。
製品実装のpath処理をPOSIX固定へ変更する承認ではなく、配布物側の対応確認は引き続き必要である。
cross compile成功と、そのOSで実際に動作を確認した証拠を混同しない。
具体的な配布検証は公開接続・配布計画で分離して定め、未実施を成功扱いしない。

## TDDの順序が崩れた原因について確認した事実

実装担当の2026-09-04の再報告では、lead personaの最初のRED/GREEN後、
read.go、minimal.go、plugins.go、budget.go、roster.goの複数の振る舞いを先に実装し、
対応するtestを後から追加した。その多くは初回からGREENだった。
go-tdd skillとagent設定には、1振る舞いずつRED→最小GREENにする指示が既に明記されていた。

親は途中報告を求めたが、各sliceのRED/GREENを受領・確認しないまま実装の進行を許し、
実装担当が実施記録をまとめた段階で不備を検知した。
したがって、直接の問題は実装手順の逸脱であり、検出が遅れた問題は親の中間gate管理にある。

実装担当は、通常のcommentaryは出したが、親への連絡toolが利用可能なtoolに現れなかったと報告した。
このtool可用性の説明は担当の申告であり、host側の原因まで独立に確認したものではない。
連絡の問題は途中確認が成立しなかった補助要因だが、testを後回しにする理由にはならない。
環境障害がTDDの順序変更を強いたという証拠はない。モデル性能や意図を原因として推測しない。

再開時は、既存のTDD要件を実際のgateにするため、1件のtest作成・RED報告で一度返却させ、
親が証拠を確認してからその1件の最小実装を渡す。途中連絡が届かない場合も、最終返却で区切れる。
過去のRED履歴を捏造せず、既に正しい条件の補足testは初回GREENと記録する。

## 承認の境界

今回のユーザー発言は検証範囲の明確化と原因説明の依頼である。
TDDの手順不備を経た現コードの採用・merge方針への明示承認とはみなさない。
回復方針の確認待ちは維持し、この記録作成に伴うコード・CI・agent設定・Issue/PRの変更は行わない。
Minimalの誤除外と警告順の本家契約違反が解消したという意味でもない。
