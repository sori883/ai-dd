# やることと未確定事項を整理してから、分割可能な実装を並列化する

状態: ユーザー指定の方向性を記録。具体的な並列実行契約・次期実装計画は未承認。

## 今回の指示

ユーザーは、提示された日常運用中心の次期マイルストーンに対し、製品が案内する作業の流れを修正した。
まずやることを決め、未確定事項を深掘りし、その後に実装する。
実装作業を分けられる場合は、AI-DLCの「ボールト」の考え方に対応して並列に進めたいとの指示である。

この指示を次期計画の優先事項とする。以前の[M2案](2026-09-07-minimal-product-milestones.md)の
複数作業・共有設計・再開・検証の鮮度は、独立した運用機能を先に増やす理由ではなく、
この作業の流れを成立させる受入条件として整理し直す案とする。
既存M1を未実装扱いに戻したり、旧33 Stageの包括承認を流用したりしない。

## 用語の確認

ローカル参照AI-DLC 2.6.123（core/tools/aidlc-version.tsを確認）では、該当する用語はBolt。
[stage-protocol.mdの用語表](../../実装_aidlc-workflows/core/aidlc-common/protocols/stage-protocol.md)に以下の区別がある。

- Unit of Work: 独立して実装できる仕事の単位。
- Bolt: 一つ以上のUnitを含む、短い実装の反復のまとまり。
- Parallel batch: 依存先が揃い、互いに依存しないUnitを並列に実行するまとまり。
- Worktree: 実装を別の作業ディレクトリへ隔離するGitの仕組み。

この版の実行順はBolt計画の単純な順次実行と同じではない。Boltと並列batchを同一視しない。
確認対象はローカル2.6.123であり、最新upstreamとの同一性は主張しない。

## 新方式での具体案

1. Intentの目的・利用者が得る結果・範囲・完成条件を決める。
2. 不明点を質問・調査で深掘りする。必要な試作を行う場合も目的を明示し、結果と判断をKDRへ記す。
   実装結果を左右する事項は合意してから着手し、後で新しい不明点が見つかれば検討へ戻る。
3. 実装をUnitへ分け、担当、変更対象、入出力の約束、依存関係、受入テストを具体化する。
4. 互いに依存しないUnitを隔離したworktreeで並列実装し、それぞれテスト→実装→テストを行う。
   分けられない仕事は直列に進める。
5. 結果を統合し、統合したコードを検証・独立レビューして同じIntentのKDRへ記録する。

一つのIntentに一つのKDRという既存合意を維持する。並列担当が同じ正本KDRを同時編集しないよう、
調整役が結果を集約する案が考えられるが、所有権と受け渡し方法は次の計画で具体化する。
共有設計・Rule・Knowledgeは引き続きSpaceのknowledge配下のOKFに置く。

## 実装前に具体化すること

Intent・Unit・Boltの対応、Unitの識別と記録場所、並列可能性の判定、変更対象の所有権、
KDRの集約担当、worktreeの作成・統合・失敗後再開、調査から実装へ進める判断基準を一つの計画にする。
本家のstate/audit/receiptをそのまま新方式へ持ち込まず、既存の最小構成の制約と両立させる。
製品が利用先で行う並列実装の設計と、本リポジトリの開発時の単独writer規則を混同しない。
この記録だけではコード・設定・Issue・PRの変更や並列実装の開始を許可しない。
