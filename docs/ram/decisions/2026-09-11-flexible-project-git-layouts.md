# 共通projectとGitの管理単位を分け、三つの配置に対応する

日付: 2026-09-11。状態: ユーザー指定の配置要件。製品コードへの反映は未実施。

## ユーザーの回答と確定した要件

ユーザーは、共通の `project/` 配下にAI-DLCとアプリを置く説明に対して、次のように回答した。

> モノレポみたいな構成ですね。
> gitはアプリごとの時もあるし、ai-dlc全体の時もある。
> なのでprojectは配下に直でsrcを置く時もある

[直前の配置指定](2026-09-11-single-project-sequential-branches-request.md)で確認待ちだったGitの管理単位は、この回答によって解決した。一つに限定せず、次の三つを対応対象にする。

1. `project/` 全体を一つのGitリポジトリとして管理し、その中に複数のアプリを置く。
2. 共通の `project/` の下で、アプリごとに別のGitリポジトリを持つ。AI-DLCの資料を管理するGitは、アプリのGitと分けられるようにする。
3. アプリ専用の中間フォルダを設けず、`project/src/` にソースコードを直接置く。

Gitリポジトリとは、変更履歴・ブランチ・コミットを一組として管理する単位である。見た目が同じディレクトリ構造でも、どこにGitの管理情報があるかによってブランチ切替の影響範囲が変わる。ユーザーへ再び「全体かアプリ別か」の二者択一を求めない。

## 共通の配置と使い方

次は説明用の配置例であり、全てのアプリや `src/` の同時作成を要求するものではない。

```text
project/
├── .codex/                 Codexのagent・hook
├── .agents/skills/         AI-DLCの進め方とCLI操作のSkill
├── aidlc/                  共通のworkflow・Space・Intent・Knowledge
├── アプリケーション1/      アプリを分ける場合のコード
├── アプリケーション2/      アプリを分ける場合のコード
└── src/                    コードを直接置く場合
```

`.git` の位置はこの共通配置の必須条件にしない。全体を一つのGitで管理する場合は `project/`、アプリ別の場合はそれぞれのアプリがGitの管理単位になる。共通管理フォルダそのものにGitがない構成も、設計・検証の対象に含める。

AI-DLCの管理元は共通の `project/` とし、コードの対象パスと、そのパスを管理するGitリポジトリを区別する。例えば同じ `アプリケーション1/` を実装しても、全体Gitならブランチは `project/` 全体で共通、アプリ別Gitならそのアプリのブランチになる。`src/` を対象にするときに、不要なアプリフォルダを要求しない。

Space、Intent、Knowledge、ADR、Rule、作業ログの共通保存先は `project/aidlc/` 配下とする。アプリ別に新しいAI-DLC一式やSpaceを自動作成する要件は追加しない。

worktreeを必須にせず、同じ作業場所では実装担当を一人ずつ割り当て、ブランチを順次扱う方向を維持する。独立レビューを担当する別エージェントは維持するが、そのための別cloneを必須にしない。既存の複数worktreeでの並列実装を削除する判断はしていない。

## 修正計画に反映する箇所

現在のコードは、管理元とコードのGitの場所が同じであることや、担当ごとに別の作業場所を持つことを前提とする箇所がある。今回の配置要件は既に全て使える状態ではない。

- `src/cmd/aidlc/minimal.go`: `--project-dir` を省略するとGitの最上位フォルダから管理元を決める。アプリ内でCLIを使ったときにも、共通の `project/aidlc/` を正しく参照する契約を具体化する。
- `src/internal/flow/store.go`、`sensor.go`、`unit.go`: 現在は一つの管理元のGitとコミットを基準にコードや結果を検査する。対象アプリのGit、ブランチ、コミット、テスト結果の対応を分ける。Intentが複数のGitリポジトリに関係する場合の保存方法と検査方法も計画で説明する。
- `src/internal/assignment/reservation.go`、`src/internal/flow/assignment.go`、`src/internal/flow/unit.go`: 管理元とworkerの別root必須条件を見直す。同じ作業場所の二重割当拒否と、終了不明の割当を自動解放しない条件は保つ。
- `src/internal/flow/review.go`: 同じ作業フォルダの別エージェントによるレビューと、レビューしたコードの版を維持する方法を具体化する。
- `src/internal/install/`、`src/internal/minimal/`、配布Skill・利用者ガイド: 共通管理元の配置、アプリ内からのCLI操作、hookの保存先、対象パスの説明を揃える。固定Codexによる通常のhook読込・信頼確認は、今回の配置ごとに検証条件を定める。

これらは修正対象の整理であり、CLI引数や永続データ形式を確定した実装計画ではない。三つの配置に対応する要求は確定しているため、次の具体計画はこの要求を前提に作成する。管理元の特定方法、複数Gitの結果保存、レビュー中の変更とブランチ切替の扱いを、利用者が読んで判断できる形にまとめる。

[worktree共有hook計画](../../design/shared-worktree-hooks-plan.md)と[担当別clone案](2026-09-11-worktree-deferral-layout-options.md)は検討履歴とする。それらの配置を今回の承認済み要件として持ち込まず、今回の共通project構成に沿って計画を組み直す。
