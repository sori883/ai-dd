# 4段階で使うSensorの整理案

状態: Proposed。製品4担当の導入後、ユーザーが「まずどういうSensorがあればよいか」の説明を依頼した。
本記録は候補の整理であり、新しい保存形式・公開CLI・Sensorの実装承認ではない。
既存の[具体案](../../design/space-reverse-okf-sensor-plan.md)を補足する。鮮度・変更不要文書の2点は未回答。

SensorはGo CLIによる機械的な検査、独立レビューは内容と根拠の妥当性の判断とする。
Sensor成功と、同じ対象版に対する独立review成功の両方が揃った場合だけ次へ進む。
全操作audit、作業日誌、本文snapshotを追加する案ではない。

## 共通の候補

1. 成果物: その段階で必要なOKF文書の実在、Space内配置、型、metadata、必須節を検査する。
2. 今回成果物: Intent専用の必須成果物はintent_idと現在Intentを照合する。共有Knowledge/Ruleの参照は区別する。
3. 鮮度と対象版: CLIの生成日時と、その成果物を作る段階の開始時刻を比較する案。
   前段階の成果物を後段階へ進んだだけで作り直させない。参照元資材の版も照合する。
   文書・コード・関連資材が変われば以前のreview passを再利用しない。日時だけでは内容の更新を証明しない。
4. ADR: アーキテクチャレベルの設計変更が必要と宣言された場合、knowledge/ADR内の対応文書を確認する。
   不要なら理由を要求し、その要否判断自体はreviewerが検査する。一律1 Intent 1 ADRには戻さない。

## 段階ごとの候補

- 目的整理＋深掘り: 目的・範囲・受入条件・制約を含む要件文書、既存資材がある場合の現状解析文書、
  次へ進む判断を妨げる未確定事項が解消されていること。現状what/howと未実装の要求を区別する。
- 実装計画: 実装と検証の対応、Unitを使う場合の担当範囲・依存・重複・base・検証方法・Bolt。
  単独実装にも計画と検証方法を要求する。
- TDD: 対象版に結び付いたテスト実行結果、必要な失敗→成功の証拠、Unitの実装成果。
  testファイルや空でないログの存在だけで実行成功としない。テストの十分性とREDの意味はreviewerが判断する。
- 統合検証: 全Unitの成果が統合先に含まれ、統合後の全体受入検証が成功していること。
  現行Knowledgeが実装後の仕様・手順を説明していることは、文書の実在・関連付けをSensor、内容整合をreviewerが検査する。

## 現状と順序

現行flow/sensor.goには目的・範囲・受入条件・blocking unknowns、OKF実在/解析/type、ADR要否、
実装計画、Unit依存/統合、コードと登録成果物の対象hashの基盤がある。
今回Intentのmetadata照合、段階開始時刻、必須文書の役割/節、参照元版の明示照合は追加候補。
テスト成果物は現状では非空の検査であり、それだけをテストの実行成功認定と説明しない。

最初は目的整理＋深掘りの出口で、必須文書・Intent対応・鮮度/参照元・ADRを揃える案を推奨する。
新4担当のうちresearcherが根拠を調査、requirementsが要件を整理、調整役がCLIで保存してSensorを実行、
reviewerが内容を検証する。workerは承認された実装を担当する。Sensor専用AIは増やさない。

実装前には、文書ごとの鮮度基準と、変更不要の過去文書を参照のみとするか明示再確認で再利用するかを確定する。
過去文書を自動で今回の成果物として合格させず、生成日時だけを空更新する操作も採用しない。
