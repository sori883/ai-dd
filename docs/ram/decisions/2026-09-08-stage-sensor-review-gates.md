# ステージ間にSensorとレビューを設ける

状態: 各ステージ間のSensor・レビューと、レビュー合格後の進捗更新はユーザー指定で確定。
具体的な検査項目・レビュー担当・保存形式・実装計画は未確定。

## 確定した要求

ユーザーは「目的整理＋深掘り → 実装計画 → TDD → 統合検証」の間に、
ADRの存在確認などのSensorとレビューを設け、レビューが通ったら進捗を進めることを指定した。
[4段階フロー](2026-09-08-four-step-flow-adr-and-progress-state.md)の遷移条件を具体化する。

推奨する順序は、現ステージの成果準備 → Sensor検査 → 内容レビュー → 合格した対象の確認 → state更新である。
不合格・検査不能・レビュー未実施のまま次ステージへ進めない。
不足や指摘は現ステージで修正し、影響する検査・レビューを再実行する。

## 各境界の検査・レビュー案

| 境界 | Sensorの機械的な確認 | レビューの内容判断 |
| --- | --- | --- |
| 目的整理＋深掘り → 実装計画 | 必要な整理内容・参照Knowledgeの存在、実装計画を妨げる未確定事項の扱い、必要なADRの存在と参照 | 目的・範囲・制約が明確か、深掘りは十分か、設計判断の理由が説明されているか |
| 実装計画 → TDD | Unit・依存・変更範囲・受入条件・テスト方針の記載、必要なADRと適用される実装許可の参照 | 計画が目的を満たすか、TDDで確かめられるか、並列分割と変更範囲は妥当か |
| TDD → 統合検証 | 対象Unitの成果回収、テスト結果と対象版の対応、必要なKnowledge・ADRの反映 | 実装の正しさ、テストの十分性、設計との整合、統合へ進めるか |

統合検証からIntent完了にも同様のSensor・レビューを置くことを提案する。
全体の受入条件・統合結果・検証対象版・Knowledgeの現行との整合を確認してから完了にする。
これは今回指定された3つのステージ境界を補う案であり、完了契約として計画へ明示する。

## 責任分担と状態

Sensorは読取り専用で、存在・形式・参照・対象版などを確認する。ファイルの存在だけで内容の妥当性は認定しない。
レビューが内容を評価し、CLIが現在のstateと検査・レビュー結果を照合して遷移を制御する。
段階は合格まで維持し、Sensor待ち・レビュー待ち・修正待ちなどは進行状況の詳細として扱う案とする。
状態名の確定一覧は後続計画で定める。

stateには検査・レビューの対象版と結果への参照、未解消の指摘など、進行制御に必要な情報を保持する案とする。
合格後に対象成果物や計画が変わった場合、古い合格をそのまま流用しない。
全操作auditや独自snapshot/receipt台帳は再導入しない。
レビュー担当は作業担当から独立したAIを候補とし、具体的な担当・合格基準・人間確認との境界は実装計画で確定する。
レビュー合格は、別途必要なユーザーの実装許可を代替しない。

ADRは[Knowledge/ADRの責任分担](2026-09-08-knowledge-what-how-adr-why.md)を維持し、
アーキテクチャ設計の理由を残す。作業報告やレビュー結果の保存先にはしない。
ADRが必要な設計判断を特定してSensorへ渡し、レビューでその必要性の見落としも確認する案とする。
ADR不要の作業に空のADRを強制しない。Knowledgeは現行のWhat・Howを表し、未実装案を現行扱いしない。

## 実装前に具体化すること

各ステージの成果物の配置と形式、ADR要否の扱い、レビュー担当・結果形式、対象版の判定、
修正後の再検査範囲、途中失敗からの復旧、並列Unitの結果集約とIntent遷移の条件を一つの実装計画にまとめる。
本家AI-DLCのSensorを助言として扱う旧契約と、新方式の必須遷移条件を混同しない。
参照版との意図的な差分と利用者への影響を計画で明示する。
今回の設計要件の合意を次期マイルストーン全体の実装許可とは扱わず、コード・設定・Issue・PRは変更しない。
