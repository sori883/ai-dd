# KDRを正本にしたUnit実行管理とSensorの案

状態: ADRの意味はユーザー回答で確定。stateとSensorは設計検討案で、実装未承認。

## 今回確定したことと依頼

ユーザーは「ADR=IntentごとのKDRへ各工程の判断・結果を記録する」と回答した。
[前の確認事項](2026-09-08-okf-reference-and-record-every-step.md)を解消し、別ADRファイルは作らない。
また、Bolt/Unit実装にstate管理が必要か検討し、KDRの存在や成果物を確認するSensorを作りたいと指定した。
以前の工程state不要という境界を理由に検討を拒まない。一方、今回の依頼は旧33 Stageや全操作auditの
包括的な再導入承認ではなく、必要な状態と検査を具体化する依頼として扱う。

## 現状

- `src/internal/minimal/session.go` は会話とIntent、未記録、実行中tool、Rule読込情報を一時保存する。
  Unitの依存・担当・worktree・統合を調整する機能ではない。
- `src/internal/kdr/document.go` と `src/internal/minimal/command.go` にKDR形式・ID・保存競合・
  index/log整合を確認する仕組みがある。各工程やUnitの記録充足を判定する契約はまだない。
- 既存 `src/internal/sensor/intent_capture.go` は旧Intent Capture向けの助言検査である。
  `context.go` は旧Stage・state・memory構成を読むため、新方式へそのまま接続する前提にしない。
  純粋な検査や安全なファイル読取りの再利用可否を実装計画で精査する。

## 推奨する構成

| 役割 | 持つ情報 | 扱い |
| --- | --- | --- |
| KDR | 目的・各工程の判断、Unit計画と依存、成果・検証・統合結果、未解決事項 | Intentごとに一つの永続的な正本 |
| 実行管理のstate | Unitを誰に割り当てたか、session/worktree、現在の実行や結果待ち | 現在の作業調整に必要な最小限の一時情報 |
| Sensor | KDR・計画・成果物・検証対象を読み、不足や不整合を返す | 読取り専用。判断記録や状態を自ら書き換えない |

状態を持たず全て調整役の記憶に任せると、二重起動・依存未成立・結果未回収を防ぎにくい。
一方、別の永続stateへKDRの計画・完了状況を複製すると、どちらが正しいか照合する負担が増える。
そこで、計画と確定結果はKDR、実行中の割当は一時管理に分ける方式を第一案とする。
KDR内のUnit識別・依存・必要成果物・結果参照は機械的に読み取れる形式を次の計画で定める。
frontmatterのOKF標準statusを工程完了の証拠として使わない。

例: Unit AがAPI、Unit Bが画面、Unit Cが結合検証を担当する。
入出力の約束を深掘りで確定した後、競合しないAとBは別worktreeで並列に実装する。
調整役が結果を受け取り、検査・レビュー・統合を行い、基準commitと結果をKDRに記録する。
CはA/Bの担当終了だけで起動せず、必要な成果が基準commitへ統合されたことを確認して始める。
Boltは一つ以上のUnitをまとめる実装反復として扱い、並列batchとは区別する。
Boltの表示は所属Unitと統合結果から導き、同じ完了情報を別の台帳へ重複保存しない案とする。

調整役一人が正本KDRへ各担当の判断・結果を集約する。workerの終了をKDR記録完了と同一視しない。
結果の未回収があれば作業完了にしない。中断後はKDR・worktree・Git・processを照合し、
一時stateだけを根拠に実行済み/未実行を決めたり、外部操作を無条件に再実行したりしない。

## Sensorの初期対象と効力の案

| 検査 | 確認すること | 不足時の提案 |
| --- | --- | --- |
| KDR | 存在、OKF形式、Intent ID対応、対象工程/Unitの必要記録 | 引渡し・完了操作を拒否し不足箇所を案内 |
| 深掘り結果 | 実装を妨げると明示された未確定事項と、解消判断の記録 | 該当Unitの実装開始を待つ。あらゆる疑問がゼロであることは要求しない |
| Unit計画 | 依存の循環・未知ID、担当と変更範囲、受入条件 | 不正な起動・並列割当を拒否 |
| 成果物 | 承認したUnit計画が指定するファイルの存在・形式・対象版 | そのUnitの引渡しや統合を完了扱いにしない |
| 検証の対象 | テスト・レビューがどのコード版に対する結果か、現在の版と一致するか | 不一致・確認不能を成功扱いせず再確認へ |
| OKF参照 | 記録されたConcept IDが解決できるか、必須Ruleの読込条件 | 欠落を示し、必要な参照・再検討へ戻す |

Sensorは「成立」「不足」「確認不能」を区別する。故障を合格として扱わない。
ファイルの存在だけで品質、テスト成功、設計の妥当性、利用者の承認を認定しない。
参照記録の存在だけでAIが内容を理解したと証明することもできない。意味の判断はAIとレビューが担う。
検査結果を受けるCLI/hookが、操作ごとの条件に従って実行・引渡し・統合・完了を許可/拒否する。
不足の修復・読取り・質問・中断の記録は妨げず、関係のないUnitまで一律停止させない。

必要成果物を全工程に固定で押し付けず、目的とUnit計画で具体的に宣言する。
各工程で行動・参照・判断・結果・残件をKDRへ記録し、空のKDRが一つあるだけで通る検査にはしない。
全検索や全toolの監査履歴、新しい独自JSON snapshot/receiptは作らない。

## 次の計画で確定する契約

この案を採用する場合、KDR内のUnit/Boltの形式、実行割当の保存先と失効・復旧、
workerの結果引渡し、依存先の統合条件、成果物指定形式、検証結果の参照方法、
Sensorごとの警告/拒否条件、並列数・変更範囲競合時の振る舞いを一つの計画にまとめる。
拒否は機械的に確認できる構造不備に限定し、判断が必要な不明点は質問へ返すことを推奨する。
Go単一バイナリ、Space配下のOKF、1 Intent 1 KDR、既存データ移行不要、外部module追加なしを維持する。
具体的な公開CLI・永続形式・実装ファイル・受入testを提示して承認を得るまで、コード・設定・Issue・PRは変更しない。
