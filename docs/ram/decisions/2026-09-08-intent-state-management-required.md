# Intent全体のstate管理を要件に加える

状態: Intent自体のstate管理はユーザー指定で必要。具体的な状態一覧・保存形式・遷移条件は設計案。

## 確定した要件

ユーザーはUnitに加えてIntent自体の状態も扱いたいと指定し、さらに「記録というかstate管理です」と補足した。
これはADR本文に現状を書くことだけではなく、製品がIntentの現在地を読み、操作と状態変更を制御する要求である。
[前案](2026-09-08-adr-name-and-unit-runtime-state.md)のUnit割当中心の説明を拡張する。
以前の工程state不要という方針は、Intent全体のstate管理を不要とする根拠にはしない。
全操作auditや旧33 Stageエンジンの再導入を要求されたとは扱わない。

## 具体化する案

Intentのstateを「作業段階」と「進行状況」に分ける。

| 軸 | 候補 | 役割 |
| --- | --- | --- |
| 作業段階 | 目的整理・深掘り・実装計画・実装・統合検証 | Intent全体で今どの作業に取り組んでいるか |
| 進行状況 | 未着手・進行中・待機中・中断中・完了・取りやめ | 実行を進められるか、終了したか |

待機には質問・承認・依存先などの理由と解除条件を持つ。Unitの一部が待機しても、他のUnitを進められるなら
Intent全体は進行中とする。作業段階はUnit別の細かな活動を一律に制限するものではない。
完了時も最後の作業段階を保持し、進行状況で完了を表す。

CLIが開始・段階変更・待機・再開・完了の要求を受け、現在stateと必要条件を確認して競合を防いで更新する。
Sensorは対象ADR、宣言された成果物、依存関係、検証対象版などを読取り専用で検査する。
調整役は状態変更の理由・判断・結果を同じIntentのADRへ記録する。
stateの正本をADRの構造化項目に置くか専用ファイルに置くかは未確定であり、重複した正本を作らない。
別ファイルとする場合はADR保存とstate更新の途中失敗を含め、復旧方法を実装前に確定する。

深掘りから実装計画へ進む時には実装を妨げる未確定事項の解消を、実装開始には適用される承認とUnit計画を、
Intent完了には対象Unitの成果回収・必要な統合・検証・ADR記録を確認する案とする。
Unit未分割の小さなIntentも扱い、Unit数ゼロだけで完了可能とは判定しない。
調査だけを目的とするIntentも目的に応じた成果と受入条件で終了できるようにする。
検証で仕様の問題が見つかった場合は理由と影響範囲を確認して深掘りへ戻れる。
状態の変更だけで人間の承認や検証成功を認定しない。

この案は本家AI-DLCとの状態・遷移の一致を確認済みとは主張しない。
状態の確定一覧、保存場所、公開CLI、Sensorの拒否条件、本家との差分、受入試験を自己完結した計画へまとめる。
今回の要件確認だけで次期マイルストーン全体の実装許可とは扱わず、コード・設定・Issue・PRは変更しない。
