# 配置Markdownからルールと知識を供給するマイルストーン

- 日付: 2026-09-04
- 状態: Accepted（ユーザーによる3段階の直接承認）
- 最初のIssue: [#89](https://github.com/sori883/ai-dd/issues/89)

## 背景と利用者が得る結果

Go版AI-DLCには工程の状態を扱う内部ライフサイクルと、本家と同じ `src/core/` に配置した
ルール・知識・工程手順の原稿140件がある。原稿を置くだけでは、担当AIが必要な本文を受け取って
読む経路にはならない。本マイルストーンでは、必要な本文の取得、工程と担当AIに応じた文書の選択、
Codex側での受け取りと実読込を順に接続する。ファイル名の一覧を返すだけを完成とはしない。

ルールは工程で守る必須の指示、知識は共通・専門分野・利用プロジェクトの参考文書、personaは
担当AIの役割を記した文書を指す。開発プロジェクトの `docs/ram/` は利用プロジェクトの知識ではない。

## 直接承認

ユーザーは、本家AI-DLC 2.6.123を基準として、次の提案に「はい」と回答した。

1. 必須ルール本文を順序付きで供給し、必須ファイルが欠けたら工程を開始しない。
2. 工程・担当AIに合わせて本家の共通知識・専門知識・利用プロジェクトの知識を選ぶ。
3. ルールの分割受領、選択した知識の実読込、工程手順の読込までCodex側につなぐ。

供給元については、さらに「供給は配置ファイルを読んでください。バイナリ埋め込みはダメです。
Markdownを変更したらそのまま適用されてほしい」と明示した。

## 固定する方針

- 供給元は配置ファイルとする。本文をGoバイナリへ埋め込まず、埋込みへのfallbackもしない。
- 再ビルド・再起動を必要とせず、次の読込みでMarkdownの変更を反映する。永続cacheやプロセス内cache
  で古い本文を使い続けない。既にAIが読んだ文脈を遡って変更する保証ではない。
- 必須ルールの分割配信途中に本文が変わった場合は、本家同様に古い続きの受領を拒否し、
  新しい読込みから全文を配信し直す。複数ファイルの同時編集に対する原子的snapshotは保証しない。
- 配置済み原稿はOKFへ変換しない。OKFは知識文書の形式であり、本家のルール・工程原稿へ
  その形式や独自metadataを追加する承認ではない。
- 本家の確認対象はローカル固定2.6.123。最新upstreamと同一視しない。
- `src/core/` の本家原文、任意欠損を許す既存 `memory.ReadSources`、純粋filterの
  `memory.BuildBundle` は、それぞれの既存契約を維持する。
- 既存の内部 `orchestrator.Next` はread-onlyのままにする。配信の継続管理と状態判定の責務を分ける。
- 人間の承認を証明するproduction入力の取得元、未対応工程の実行能力を省略する判断は含めない。
  knowledgeを読めることを、工程実行や承認を許可する証明にしない。
- 標準ライブラリだけを使用し、外部module/tool、有料service、認証情報や追加権限を導入しない。

## 実施順と品質gate

最初に必須ルール本文readerを小さなIssue・PRとして完成させる。次に工程・agentごとの知識選択を
扱い、最後にGo側の配信とCodex側の実読込を接続する。具体的なpackage、受入条件、確認済み本家契約は
各Issueの詳細計画へ記録する。新しい重大な公開API・永続data・安全性の選択が判明した場合は、
包括承認を広げて解釈せず、根拠と影響を示して確認する。

各PRは単独writerのTDD、固定差分の独立review、安定後のread-only final、現在headのGitHub checks成功、
merge、main反映とIssue closeを満たす。読込順、欠損、不正encoding、本文更新、大きな文書と分割受領、
実際の読込経路をそれぞれ観測可能なtestで確認する。

## 以前の決定との関係

- [薄いライフサイクル](2026-09-03-thin-lifecycle-milestone.md)に残したproduction供給元の
  「binary埋込みか配置ファイルか未決」という部分を、配置ファイルのみへ置換する。
  `HUMAN_TURN`のproduction取得元と未対応工程のfail-closed境界は変更しない。
- [core配置](2026-09-04-aidlc-core-layout.md)の「実行基盤と未接続」の境界は、このマイルストーンで
  供給の接続を実装する範囲に限って更新する。原文保持と本家配置の方針は維持する。
- [ロードマップ](2026-09-03-aidlc-implementation-roadmap.md)のOKF統合は、本家原稿のOKF化を
  前提とせず、まず通常Markdownの供給を作り込む順序とする。将来の利用プロジェクト知識への
  OKF適用方式を、この回答だけで確定しない。

## 確認済みの根拠

固定実装の `core/tools/aidlc-steering.ts:55-115` はactive Spaceと任意の `AIDLC_RULES_DIR` から
必須本文を毎回読み、missing/read/UTF-8 errorではbundle全体を不成功にする。
`aidlc-graph.ts:604-697` はorg→team→project→該当phaseの加算型ルール順を定める。
`aidlc-orchestrate.ts:2740-3106` はpersona・共通知識・agent知識・Space知識の一覧と上限を扱う。
同ファイル `3427-3728,8343-8458` と `tests/unit/t248-steering-content-delivery.test.ts:626-696` は、
分割配信中にルール・state・routeが変わると古い継続を拒否する根拠である。
配置版 `.agents/skills/aidlc/SKILL.md:78-128` は、ルール全体を保持してから知識、工程手順、
入力成果物を実際に読む受け手を示す。

## 後続実装前の確認待ち

2026-09-04の調査で、次の2点をユーザーへ非同期で確認した。本文readerのIssue #89は
供給元を注入する独立部品なので実装できるが、この回答がないまま後続の公開契約を確定しない。

1. 即時反映の対象が、開発用 `src/core/` のMarkdownそのものか、利用先へ配置した
   `.codex/` と `aidlc/spaces/` 配下のMarkdownか。ファイル供給・埋込み禁止は確定済みであり、
   再確認しているのは編集から反映までの接続先だけである。
2. 知識ファイルの列挙順を、Go標準ライブラリで実装できる既存のUTF-16 code-unit順へ統一してよいか。
   本家2.6.123の `aidlc-orchestrate.ts:2749-2787` はlocale指定なしの `localeCompare` であり、
   固定snapshot内にBun・ICU・localeの保証はない。本家の順序testはlowercase ASCIIのみである。
   提案の理由は実行環境によらない再現性と外部module回避。大文字小文字・日本語等のファイル名では
   本家との順序や8 KiBの一覧上限で残る文書が変わり得る、意図的な仕様差分として確認する。

確認済みの本家testは `tests/unit/t314-minimal-scope-performance.test.ts:45-105` と
`tests/unit/t248-steering-content-delivery.test.ts:861-1084`。この段階では新しい文書順を採用せず、
供給元の探索、知識roster、CLI接続、利用先への配布も変更していない。回答後は新しい記録へ
選択・理由・影響を残して、後続Issueの実装許可を確定する。
