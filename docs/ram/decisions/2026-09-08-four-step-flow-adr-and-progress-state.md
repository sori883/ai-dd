# 4段階のフローとADR・進捗stateの責任を確定する

状態: ユーザー指定による方針確定。具体的なCLI・保存形式・遷移条件と実装計画は未確定。

## 確定したフロー

1. 目的整理＋深掘り
2. 実装計画
3. TDD
4. 統合検証

目的整理と深掘りは一つの段階として扱う。TDDは失敗するテスト、実装、テストによる確認と
必要な整理を反復する段階である。分割可能な作業はUnitとして計画し、独立したUnitを並列に進める。
どの段階でも必要に応じてOKFを検索・参照する。

## ADRとstateの責任

ユーザーは「ADRに記録することはアーキテクチャレベルの設計変更意図」「作業記録は行わなくて良くて、
その代わりになるのが進捗記録=state管理」と指定した。

- ADR: アーキテクチャレベルで何をなぜ変更するかという設計変更意図を記録する。
  変更の背景、採用判断、理由、影響を説明する。通常の試行・作業経過・各工程の実施報告は要求しない。
- state: IntentとUnitの進捗を製品が管理し、段階変更、待機、中断、再開、完了を制御する。
  ADRの更新を通常作業の終了条件にはしない。
- Sensor: state変更に必要な成果物・検証結果・依存条件を確認する。
  ADRは設計変更意図が記録されるべき変更に対して確認する。単なるADRファイルの存在を全作業の必須条件にはしない。

stateに持つ候補は、Intentの現在段階・進行状況、Unitの割当・依存・進捗、待機理由・再開条件、
成果物と検証対象版・結果への参照である。詳細なテストログや全操作履歴の複製は要求しない。
進行状況の候補値とTDD内部のRED/GREEN等を永続stateにするかは、まだ承認済み契約ではない。
承認や検証結果への参照があることだけで、その有効性を認定しない。

## 置換対象と実装への影響

この決定は以下の記録にある各工程の作業記録必須化とフロー案を置換する。

- [Intent全体のstate管理案](2026-09-08-intent-state-management-required.md)
- [ADR名称とUnit実行state案](2026-09-08-adr-name-and-unit-runtime-state.md)
- [各段階でのOKF参照と記録](2026-09-08-okf-reference-and-record-every-step.md)の作業記録要求。OKF参照方針は維持する。
- [Unit実行管理とSensor案](2026-09-08-kdr-unit-state-sensor-proposal.md)のADRへの計画・進捗集約と一律記録必須化。

過去のM0/M1にある「1 Intentにつき記録文書を必ず作り、一般操作後に作業記録を更新する」契約は、
今後の製品の要件としてそのまま引き継がない。既存実装が変更済みであるとは扱わない。
ADRが不要なIntentに空のADRを強制することや、設計変更のないテスト修正をADR未更新で拒否することは、
今回の責任分担に合わない。ADRの作成単位・件数・Intentとの対応の最終形式は、次の契約で具体化する。
stateの保存先・形式、Unit計画の正本、ADRが必要かの判断とSensorの確認範囲も実装前に明示する。
旧記録・既存ファイルは削除せず履歴を保持する。

Go単一バイナリ、Spaceのknowledge配下のOKF、外部Go module追加なしの方針は維持する。
この要件訂正を次期マイルストーン全体の実装許可とは扱わない。
