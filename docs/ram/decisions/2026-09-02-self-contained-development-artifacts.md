# 計画・Issue・PRを自己完結した分かりやすい文章にする

- 日付: 2026-09-02
- 状態: Accepted
- 対応Issue: #51

## 背景

実装計画の承認依頼やGitHubのIssue・PRは、作成までの会話を知っている人には理解できても、
初めて読む利用者や後続の開発者には、なぜ必要な変更なのか、何が利用可能になるのか、どこまで
承認・実装されたのかが伝わりにくい場合があった。リンク先やコード識別子だけで説明すると、
読む人が複数の資料をたどり、技術用語の役割を推測しなければならない。

## 決定

今後生成する実装計画とその承認依頼、Issue本文、PR本文は、過去の会話やリンク先を読まなくても、
初心者が次の内容を理解できる自己完結した文章にする。

- 現状の問題と背景
- 変更の目的と、利用者や後続の開発者が得る結果
- 正式な技術用語やコード識別子と、その初出時の平易な役割説明
- 承認対象または実装済みの範囲と、判断に重要な境界
- 観測可能な受け入れ条件、確認結果、検証証拠

関連Issue、PR、計画、コードへのリンクは根拠として添えるが、本文に必要な説明の代わりにはしない。
通常の未実装機能は列挙せず、安全性、互換性、移行、利用条件、承認範囲の誤解を防ぐために必要な
境界だけを記載する。

## レイヤー別の責務

- `AGENTS.md`: 実装計画・承認依頼・Issue・PRに共通する高位原則を定める。
- `implementation-planning` skill: 計画の冒頭要約、用語説明、承認で許可される変更、固定する境界、
  残る判断を具体化する。既存のscope、ownership、TDD、validation、risk、承認gateは維持する。
- `github-pr-workflow` skill: Issue・PRに共通する自己完結性とリンク非依存の原則を定め、形式固有の
  手順はreferenceへ振り分ける。
- Issue作成referenceとtemplate: 現状の問題、目的、利用者への効果、具体的な対象・受け入れ条件、
  承認範囲の要約を促す。
- PR作成referenceとtemplate: 変更の必要性、利用者向け結果、実装済み範囲、受け入れ結果、検証証拠を
  PR単体で理解できるようにする。

## 適用範囲

この方針は、本決定以降に新しく生成または内容を更新する計画、承認依頼、Issue、PRへ適用する。
過去の成果物は履歴として保持し、この決定だけを理由に一括して書き換えない。

## 変更しない箇所と理由

- custom agent設定は変更しない。計画担当は既に`implementation-planning` skillを使用するため、
  同じ規則をagent設定へ重複させると将来の不一致を生む。
- `docs/agent-workflow.md`は変更しない。agent間のhandoffと停止条件を定める文書であり、成果物の
  読みやすさは各skillの責務である。
- skillの`agents/openai.yaml`は変更しない。skillの表示名や呼び出し方ではなく、生成する文章の契約を
  変更するためである。
- 既存のIssue・PR・計画は変更しない。履歴の意味を後から変えず、今後の生成結果から改善する。

## 検証方針

- 変更した2つのskillを`skill-creator`の`quick_validate.py`で検証する。
- `git diff --check`で空白エラーを検出する。
- 最終確認では、過去の会話を渡さずに計画・Issue・PRのサンプルを生成し、独立したレビュー担当が
  成果物だけから背景、目的、利用者効果、範囲、受け入れ条件を理解できるか評価する。
- サンプルはGitHubへ投稿せず、文言の完全一致を検査する固定テストも設けない。

## Forward-test実施記録

会話履歴を与えずに計画、Issue、PRを生成した初回のforward-testでは、全体として背景、目的、
利用者効果、実装範囲を理解できた一方で、次の不足を確認した。

- 計画に記載した、複数ファイルが同時に変更された場合のtransactional snapshot非保証がIssueとPRへ
  引き継がれなかった。transactional snapshotは、複数ファイルを同じ時点の一まとまりとして読む保証を
  指す。
- Issueに記載したproject root選択契約がPRでは曖昧になった。project root選択契約は、処理対象となる
  プロジェクトの基準ディレクトリをどの規則で選ぶかを定めるものを指す。
- PRに記載したrace検査と`go vet`の対象範囲が曖昧で、どのpackageを検証した証拠か判断できなかった。
- 計画にはcursor、registry、auditなど、承認判断に不要または役割説明のない補助用語が残った。

この結果を受け、計画とIssue・PRの作成前に初参加者の立場で読み直すcompleteness pass、計画から
IssueおよびIssueからPRへの重要条件の継承、受け入れ条件と結果の対応付け、検証コマンドまたは対象範囲の
明確化をskill、reference、templateへ反映した。修正後の再forward-testは未実施であり、その結果を
確認するまでは最終的な成功とは扱わない。

## リスク

- 説明を増やしすぎると、重要な判断が埋もれる可能性がある。冒頭を平易な要約とし、通常の
  未実装項目を列挙しないことで抑える。
- 共通原則を複数箇所へ重複させると、更新時に内容が食い違う可能性がある。高位原則、skill共通規則、
  形式固有referenceとtemplateへ責務を分ける。
- 用語を平易に言い換える際に正式な意味を失う可能性がある。正式名称や識別子は保持し、その役割を
  初出時に補足する。
