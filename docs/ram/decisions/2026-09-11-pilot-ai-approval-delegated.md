# パイロットの利用者役と承認回答を外側AIへ委任する

日付: 2026-09-11。状態: Accepted。Issue #163。

## ユーザーの回答と変更理由

ユーザーは、段階ごとのテスト承認を別のAIが代行できるか、通常hookの検証もできるかを確認した。
「今回のhelp改善パイロットに限り、私が試験用の承認役を代行して、hook検証も含めて進めてよいですか」
という具体案へ「じゃあちょっとお願いしてもいいですか。」と回答した。
これを今回の試験に限定した直接委任として記録する。各回の人間回答を待つ条件だけを置き換える。

置換対象は latest-workflow-pilot-plan.md の人間実回答必須条件と、
2026-09-11-latest-pilot-discovery-progress.md の後続承認待機条件。
初期化で既に受け取った人間回答の履歴は変更しない。製品一般の承認仕様は変更しない。

## 実施範囲と役割

- 対象は workflow-pilot / Intent 915a62dd6391fbab3e08a5707309d687 のcheck help改善。
- 外側の親AIが利用者役として要求、成果、Sensor、独立reviewを確認して試験用回答を生成する。
- pilot側の通常Codexは製品のメインAIとして担当をnative起動し、実際の承認待ちで停止する。
- 回答は停止後の新しい通常会話入力で渡す。実UserPromptSubmitのsession/turnと現在request/targetへ結び付ける。
- 各回答の引用に「AIによる試験用承認」を含める。本人による各成果の確認や本人認証の証拠とはしない。
- 対象の2つのGo file、6段階、同範囲の修正・再実行、独立review、final、PR/checks/mergeの境界は従来どおり。
- 範囲外の製品仕様、外部module、認証・権限、復元不能なruntimeの破棄を代理判断する委任ではない。

## hookの検証

通常の信頼済み配置を使う。hookを直接呼んだ模擬イベント、state直接編集、trust迂回で成功を作らない。
承認待ちで無害な専用canary作成を1回試し、PreToolUseの拒否とfile非存在を確認する。
現在stageで許可されない担当のnative起動も1回試し、起動前拒否を確認する。
想定外に通った場合はその事実を失敗として記録し、別経路で拒否を装わない。
正常なnative担当起動は実dispatchと応答を照合する。
回答後は通常の承認CLIとfinish、操作後のruntime、Stop後の実プロセス終端を照合する。
Stopや結果提出だけでworker停止・解放を推定しない。

## 保存・受入・復旧

生証拠はpilotのaidlc/evidence/latest-pilot/へ、承認履歴は通常製品stateへ保存する。
親の決定・委任元・試験入力・観測した拒否/許可/未確認事項を対応付ける。
開発RAMと計画はrecords checkoutの親単独writerが更新し、承認待ちのpilot/review対象を変えない。
実案件がcompletedとなり、全段階の実Sensor・実review・試験回答とhook証拠を照合して初めて完走とする。
既知の並列読取り残存と子の途中通知拒否は未解決のまま保持し、今回のhelp変更に混入させない。
中止時もstate・証拠を保持する。人間承認へ戻す場合は以後の要求から適用し、既存AI回答を人間回答へ書き換えない。
