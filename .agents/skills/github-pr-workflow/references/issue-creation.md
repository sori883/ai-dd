# Issue作成

実装Issueを、承認済み計画と実装・PRをつなぐ日本語の契約として作成する。

## 作成前

1. GitHub repository、default branch、認証状態を確認する。
2. リポジトリ規則が計画承認を要求する場合は、明示承認と承認された範囲を確認する。
   承認がなければIssueを作成せず、計画または承認を先に求める。
3. OpenとClosedの両方から、同じ目的・branch・機能に対応するIssueを検索する。
   同一Issueがあれば新規作成せず、その番号、状態、再利用可否を報告する。
4. 作成がユーザーの依頼または承認済みフローに含まれることを確認する。

## 分類ラベル

このリポジトリでは、Issueの主要な成果に応じて次の分類ラベルを必ず1つ付ける。

| ラベル | 使う場合 |
| --- | --- |
| `機能開発` | AI-DLC本体のCLI、API、保存形式、実行時挙動などを追加・変更・修正する |
| `ユーザーリクエスト` | skill、custom agent、技術分析、文書、開発運用、設定などを整備し、AI-DLC本体の挙動を変更しない |

- 変更ファイルの種類ではなく、Issueの主要な成果で判断する。製品機能に必要なテストや文書を
  同時に変更しても `機能開発`、skill整備に必要な文書を同時に変更しても
  `ユーザーリクエスト` とする。
- `機能開発` と `ユーザーリクエスト` を同じIssueへ同時に付けない。両方に見える場合は、
  Issueを分けるか、主要な成果をユーザーへ確認する。
- `bug`、`documentation` などの補助ラベルは、根拠がある場合に分類ラベルと併用できる。
- 作成前に2つの分類ラベルがrepositoryに存在することを確認する。不在の場合は
  `enhancement`等で代用せず、repository規則が変更されていないか確認して報告する。
- 既存Issueを更新するときも分類ラベルがちょうど1つか確認し、未付与なら同じ基準で付ける。

## 本文契約

リポジトリの `.github/ISSUE_TEMPLATE/implementation.md` があれば構造を再利用し、
少なくとも次を具体化する。

- 現在どのような問題や不足があり、なぜ対応が必要なのか
- 何を達成し、利用者や後続の開発者がどのような結果を得るのか
- 対象となる利用者向け挙動、パッケージ、文書
- 観測可能な受け入れ条件
- 検証方法
- 計画の承認日または承認記録と、承認された変更範囲・重要な境界の要約
- 依存Issueやblocker
- 本家AI-DLCと意図的に異なる仕様・挙動がある場合だけ、その内容と影響

過去の会話、計画書、関連Issueへのリンクだけで背景や承認範囲を表さない。必要な事実と判断は
Issue本文にも短く記載し、リンクは詳細な根拠として添える。正式な技術用語やコード識別子は
保ち、初めて出る箇所で「何をするものか」を平易に説明する。独立した用語集は、本文中の説明
だけでは理解しにくい用語が複数ある場合に限って設ける。

承認済み計画と本文を照合し、公開する挙動やデータの契約と、安全性、互換性、移行、利用条件、
承認範囲に影響する重要な条件をIssueへ引き継ぐ。該当する条件は対象または特記事項として具体化し、
通常の未実装機能をnon-goalとして追加しない。

通常の未実装機能や「今回は作らないもの」を列挙しない。安全性、互換性、移行、利用条件に
影響する特殊な制約がある場合だけ、判断に必要な特記事項として記載する。段階的な未実装、
言語移植による内部差分、未調査の差分を「意図的な差分」として水増ししない。外部moduleや
toolの追加がある場合は、必要性と承認状態を明記する。

タイトルと本文は日本語を基本とし、対象は変更する挙動や成果物を特定できる粒度で、受け入れ
条件は完了後に真偽を判定できる書き方にする。承認欄は日付や会話リンクだけにせず、その承認で
実装してよい範囲と、固定された重要な境界を要約する。未解決の重要な判断が残る場合は、承認済み
の内容と混同しないよう明記する。
分類以外のラベル、担当者、milestone、Issue typeは、既存規則またはユーザー指定がある場合だけ
設定する。

## 作成と確認

1. 対話promptへ依存せず、確認済みのタイトル、本文、分類ラベルを明示してIssueを作成する。
2. 応答が不明確または失敗した場合は、再作成前に検索して作成済みか確認する。
3. 作成後にIssueを読み直し、番号、状態、タイトル、本文、分類ラベル、URLが意図どおりか
   確認する。2つの分類ラベルのうち、選択した1つだけが付いていることを確かめる。
4. ユーザーへIssue番号とURLを日本語で報告する。

Issue本文は実装中に範囲を勝手に広げる許可ではない。承認済み計画にない変更が必要なら、
Issueを更新する前に新しい判断と承認を得る。
