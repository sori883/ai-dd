# Issue作成

実装Issueを、承認済み計画と実装・PRをつなぐ日本語の契約として作成する。

## 作成前

1. GitHub repository、default branch、認証状態を確認する。
2. リポジトリ規則が計画承認を要求する場合は、明示承認と承認された範囲を確認する。
   承認がなければIssueを作成せず、計画または承認を先に求める。
3. OpenとClosedの両方から、同じ目的・branch・機能に対応するIssueを検索する。
   同一Issueがあれば新規作成せず、その番号、状態、再利用可否を報告する。
4. 作成がユーザーの依頼または承認済みフローに含まれることを確認する。

## 本文契約

リポジトリの `.github/ISSUE_TEMPLATE/implementation.md` があれば構造を再利用し、
少なくとも次を具体化する。

- 目的と背景
- 対象となる利用者向け挙動、パッケージ、文書
- 観測可能な受け入れ条件
- 検証方法
- 計画の承認日または承認記録
- 依存Issueやblocker
- 本家AI-DLCと意図的に異なる仕様・挙動がある場合だけ、その内容と影響

通常の未実装機能や「今回は作らないもの」を列挙しない。安全性、互換性、移行、利用条件に
影響する特殊な制約がある場合だけ、判断に必要な特記事項として記載する。段階的な未実装、
言語移植による内部差分、未調査の差分を「意図的な差分」として水増ししない。外部moduleや
toolの追加がある場合は、必要性と承認状態を明記する。

タイトルと本文は日本語を基本とし、受け入れ条件は完了後に真偽を判定できる書き方にする。
ラベル、担当者、milestone、Issue typeは、既存規則またはユーザー指定がある場合だけ設定する。

## 作成と確認

1. 対話promptへ依存せず、確認済みのタイトルと本文を明示してIssueを作成する。
2. 応答が不明確または失敗した場合は、再作成前に検索して作成済みか確認する。
3. 作成後にIssueを読み直し、番号、状態、タイトル、本文、URLが意図どおりか確認する。
4. ユーザーへIssue番号とURLを日本語で報告する。

Issue本文は実装中に範囲を勝手に広げる許可ではない。承認済み計画にない変更が必要なら、
Issueを更新する前に新しい判断と承認を得る。
