# 実行担当へ渡せる計画

最初に問題を起こす入力と、実装後に利用者が見る結果を書く。次に既存の入口・test・設定・決定を根拠として選んだ方法を示す。「テストする」だけで終えず、command、成功条件、失敗時の動作を対応付ける。

UnitはUIだけ・databaseだけといった層の切り分けより、結果が端から端まで見える縦の単位を優先する。Unit間の依存、writer所有file、統合前に必要な結果、元へ戻す必要がある操作を明記する。独立に出荷できない細片を増やさない。

計画のreviewでは、完成条件、実現可能性、範囲、test可能性、重大な前提を一度照合する。コードで確かめられる主張は実装とtestへ辿り、docsの古いpathやversionをそのまま採らない。重大な未解決判断だけを選択肢と影響付きでメインAIから利用者へ提示する。任意の自己採点を上げるために要件を追加しない。

本文だけで別sessionが実行できるよう、会話中の訂正と根拠も書く。共有保存・承認はAI-DLCの既存経路へ戻し、Issue trackerへ独自に公開しない。
