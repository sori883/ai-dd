# 観測する境界と縦の実装

testが読むのは利用者が使う公開境界と、その戻り値・観測可能な副作用。たとえば購入処理なら「有効なcartで購入が成立する」を検査し、内部helperが呼ばれる回数を契約にしない。既存の境界で結果を確認できるなら新しい内部APIを増やさない。

失敗する一つの動作→最小実装→同じtestの成功を縦に通してから、次の動作へ進む。すべてのテストを先に書くと、仮想の内部構造に結合したテストが増える。期待値は仕様や独立した具体例から取り、実装と同じ計算をtestへコピーして正解を作らない。

外部API・時刻・不安定なI/Oは必要な境界で代替できるが、内部の実装部品をmockしてテストの中心にしない。依存先の失敗も公開境界の結果として検証する。テスト名と語彙は既存の共有用語・判断に揃える。レビューで構造を整理するときも、観測契約を維持する。
